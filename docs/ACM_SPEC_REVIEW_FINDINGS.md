# ACM 规格文档评审发现（v2.0 vs v1.1）

<!-- 评审对象：ACM_PROJECT_SPEC_v2.0.md（治理规格）与 ACM_PROJECT_SPEC_FINAL_v1.1.md（实现参考）
     评审日期：2026-08-17 | 方法：逐节交叉比对 + 各文档内部一致性检查 -->

## 总体结论

两份文档的**原则层高度一致**：三条公理、Scope 边界、回滚三元模型（Manifest/Journal/Snapshot）、退出码、P0 选型、路线图分期均对齐，交叉引用（v2.0 → v1.1 §6/§7.5.1/§7.6/§8）全部有效。未发现根本性方向矛盾。

但存在 **1 处图式矛盾、若干措辞级不一致、以及 4 个两份文档共同的设计 Gap**（其中 TOCTOU 指纹与字段哲学的张力、`use` 跨 Agent 部分失败语义缺失，建议在编码前裁决）。

## 一、两文档之间的不一致

### 1.1 Desired State 在流水线中的位置（图式矛盾，建议修 v1.1）

- v1.1 §7.1 流水线：`Profile Resolution → Desired State → Adapter（语义编译）→ ChangeSet`，Desired State 位于 Adapter **之前**。
- 但两文档对 Desired State 的定义均为"Active Profile **经 Adapter 编译后**的字段级期望状态"（v1.1 §7.1 正文、v2.0 §3.1 表）。
- v2.0 §3.1 的图（Adapter 编译 → Desired State → Safety Engine）与定义一致；v1.1 的图与自己的定义矛盾。字段级期望状态天然是 per-Agent 的，必须在 Adapter 之后。

### 1.2 v2.0 状态语义的"三组关系"框架不完整

v2.0 §4.1 声称状态语义"围绕三组关系定义：安装/接管与否、Current vs Desired、有无外部漂移"，并要求与 v1.1 §7.6 的 7 态枚举对齐。但 §7.6 中 `CONFLICT` 与 `ERROR` 无法由这三组关系推导（二者分别是环境冲突和配置损坏维度）。v2.0 的表述过简，应补第四组关系（环境/健康状态）。

### 1.3 `acm init --force` 与"绝不破坏现有配置"的张力

- v2.0 §4.2：init "绝不静默修改，**绝不破坏现有配置**"（无保留条件的绝对措辞）。
- v1.1 §10.1：config 已存在时 init 提供"覆盖"选项，`--force` 跳过提示**重新生成**（即丢弃现有 config.toml）。

若 v2.0 的"绝不"意为"绝不静默破坏"，则应明确写出，否则与 v1.1 的 `--force` 覆盖语义字面冲突。

### 1.4 v2.0 对 v1.1 细节的遗漏（非矛盾，列出备查）

- L1 范围：v1.1 含 `org_id`，v2.0 §2.2 未列。
- v2.0 §7 Phase 2 清单遗漏了 v1.1 §12 规划的：`acm config migrate`、`acm profile list/show/create`、`acm use-vmr`、`acm vmr status`。
- 全局选项：v1.1 还有 `--show-secrets`、命令级 `--agent` / `--against` / `--to-tx` / `--snapshot`，v2.0 未提（v2.0 自称"语义非界面规格"，可接受，但 `--show-secrets` 承担"明文 opt-in"原则的落地，值得在 v2.0 §4.2 点名）。

## 三、共同 Gap（两份文档均未覆盖，建议编码前裁决）

### 3.1 整文件指纹校验与"管字段不管文件"哲学的张力（最重要）

- 漂移的**定义**是字段级："管理字段的磁盘值 ≠ ACM 最后写入值"（v2.0 §3.1、v1.1 §7.5.2）。
- 但 TOCTOU 防护的**实现**是整文件哈希 H0（v1.1 §7.5.1 阶段 3；v2.0 §3.4 不变量 4 同意"校验磁盘未被外部改动"）。
- 后果：外部对**非管理字段**的任何写入（文档自己反复强调 Agent 运行时会持续写状态：权限、插件记录、会话缓存）都会导致指纹不匹配 → 整体中止并报 drift → 需 `--force`。这与"未管理字段必须无损保留、漂移仅指管理字段"的语义直接冲突，且 Codex/Pi 属 BLOCK 级进程守护，运行中触发概率不低。
- 需裁决：指纹比对是否应限定为管理字段语义值（结合阶段 2 的解析树），或明确"窗口内外部写入一律阻断"是有意为之的保守策略并回写措辞。

### 3.2 `acm use` 跨 Agent 部分失败语义未定义

- 一次 `use` 投影到 N 个 Agent = N 个独立事务（journal/快照均按 Agent 分目录），无跨 Agent 原子性。
- 未定义：`~/.acm/state/active` 的写入时机（投影前？全部成功后？）；Agent A 成功、Agent B 被 drift 阻断时，active 是否已切换、status 如何呈现（A=SYNCED、B=DRIFTED？）、重试路径是什么。
- 这直接影响 v2.0 §4.3.5 / v1.1 §14 的"≤3 条命令"成功标准的可判定性。

### 3.3 rollback 与激活 Profile 的关系未定义

- rollback 回滚字段值，但 `active` 仍指向当前 profile → 回滚完成后立即 OUT_OF_SYNC。rollback 是否同步回退 active（journal 中记录来源 profile，具备条件）未说明。同理 `use --agent <id>`（v1.1 §10.1 中 MVP 已有此参数）是否修改全局 active 也未说明。

### 3.4 "适配器物理上无法绕过安全语义"是过度声明

- v1.1 §7.1 与 v2.0 §3.4 均断言适配器"**物理上**无法绕过"安全语义。事实是：适配器是同进程 Python 代码，Phase 2 更将支持用户 `~/.acm/adapters/*.py` 经 importlib 热加载——任意适配器都可以直接 `open()` 写文件。
- 该保证实际由架构约定 + review + 金样/负面测试背书，不是物理隔离。建议措辞降级为"架构上不赋予写盘路径，由测试与审计保障"，或引入真正的进程/权限边界（若坚持原措辞）。

## 四、次要 Gap（记录在案）

1. **快照保留数"可配置"（v1.1 §7.5.3）无落点**：config.toml 被严格限定为仅 providers/models/profiles 声明式内容（D3），此类运行时设置放哪（环境变量？state 下的 settings？）未定义。
2. **CONFLICT 状态波及只读命令？** §7.6 将"Agent 进程运行中"纳入 CONFLICT 定义，但 status/diff 等只读命令本不应被运行中的 Agent"冲突"。阻断语义应仅限写入命令，状态枚举需澄清。
3. **verify() 缺席主流水线**：Adapter 四职责含 verify（落盘后断言），但 §7.1 十层流水线在 Atomic Write / Journal 之后没有 verify 环节。
4. **未安装 Agent 的处理**：detect 以"配置目录存在"为主判据，则已安装但从未运行的 Agent 记为 NOT_DETECTED——是否符合直觉可接受，但建议在矩阵或文档中明示这一取舍。
