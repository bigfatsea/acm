## A 级：两文档直接冲突（必须裁决）

### A1. 进程守护机制：v2.0 已废除，v1.1 仍大量保留 ⚠️ 最严重

| 位置 | 内容 |
|---|---|
| v2.0 §4.1 | "**不引入**高误判、高平台兼容成本的**外部进程扫描阻断机制**；写操作通过排他写锁与原子替换自然保障并发安全" |
| v1.1 §7.1 | 流水线含"进程"检查层 |
| v1.1 §7.5.1 | 阶段 1 第 1 步"进程守护：按策略（§7.5.5）提示或警告" |
| v1.1 §7.5.5 | 完整的 BLOCK/WARN 分级进程守护表（pgrep/tasklist） |
| v1.1 §10.2 / §10.3 | 退出码 2 场景含"进程冲突"；标准文案含进程冲突提示 |
| v1.1 §13 风险表 | "进程守护分级 + 漂移检测 + 指纹校验 + 快照兜底（四层防御）" |
| v1.1 D2 / 附录 A.2 | "进程检测用标准库（pgrep/tasklist），不引入 psutil" |

**注意**：v1.1 自身也不一致——§12 Phase 1 交付清单（三阶段提交、漂移检测、指纹校验、并发锁、崩溃恢复、快照、密钥掩码）**已不含进程守护**，说明 v1.1 修订时删了一半、漏了另一半。

**裁决建议：以 v2.0 为准，全面删除 v1.1 的进程守护内容**。理由：
1. 治理规则明确冲突时改实现参考；
2. v2.0 废除理由充分：`pgrep` 按进程名匹配误判率高、Windows `tasklist` 兼容成本大，而进程守护防的场景（Agent 退出时覆写）本就由漂移检测 + 指纹校验 + 快照兜底覆盖，进程扫描是冗余的第三道防线；
3. 具体修订：删 §7.5.5 全节、§7.5.1 阶段 1 第 1 步、§7.1 流水线"进程"字样、§10.2 退出码 2 的"进程冲突"场景、§10.3 进程冲突文案、§13 对策改为"漂移检测 + 指纹校验 + 快照兜底（三层防御）"、D2 删"进程检测用标准库"句、附录 A.2 一.9 补注"v2.0 已废除"。

### A2. 动态适配器热加载：v2.0 明确拒绝，v1.1 仍列为 Phase 2 交付

| 位置 | 内容 |
|---|---|
| v2.0 §5 | "所有官方与社区适配器统一作为代码内置（Built-in），**拒绝动态代码反射执行的安全隐患**"；"新增适配器 = 源码内置模块 + 金样 fixtures 门禁合并" |
| v1.1 D7 | "MVP 不实现热加载，但 **Phase 2 交付 importlib 加载器** + 协议文档 + 模板" |
| v1.1 §7.2 / §7.7 | 组件图与目录布局含"用户适配器 `~/.acm/adapters/*.py`（Phase 2 动态加载）" |
| v1.1 §8 P2 / §12 Phase 2 | "用户适配器热加载" 作为交付项 |

**裁决建议：以 v2.0 为准，删除 v1.1 的热加载规划**。理由：
1. 运行时加载任意本地 `.py` 等于执行任意代码，与 CLI 安全工具的信任模型冲突；社区适配器走"PR + 源码内置 + 金样门禁"即可满足 §1.1 P2"低成本接入"目标；
2. 修订：v1.1 D7 改写为"已由 v2.0 裁决否决，社区适配器一律源码内置"；删 §7.2/§7.7/§8 P2/§12 Phase 2 相应条目，`~/.acm/adapters/` 目录不再预留；
3. **v2.0 自身也需修**：§1.1 P2"开放插件化与社区扩展"的"插件化"措辞暗示运行时插件，与 §5 自相矛盾，建议改为"开放社区贡献内置适配器"。

### A3. `release` 语义：两文档内部各自矛盾，四种表述分成两派

| 立场 | 位置 | 表述 |
|---|---|---|
| **保留当前值**（仅解除托管） | v2.0 §4.2 | "解除 ACM 托管，清空状态记录；**物理文件原地保留**" |
| | v1.1 §7.5.2 | "原位物理文件**完整保留**；ACM 全新创建且无用户内容的文件安全清理" |
| **恢复 pre-ACM 状态**（撤销一切注入） | v1.1 §10.1 | "**按管理清单恢复 pre-ACM 状态**，清空清单，零残留" |
| | v1.1 附录 C | "按管理清单**移除 ACM 注入的一切**，恢复 pre-ACM 状态" |
| | v1.1 §12 验收 #6 | "release 后三 Agent 配置**与 pre-ACM 状态一致**" |
| | v1.1 §9 | "一键解除所有 Agent 与 VMR 的绑定，零残留" |

两种语义差异实质："保留当前值"意味着 release 后 Agent 仍指向 ACM 投影的模型（仅不再被管理）；"恢复 pre-ACM"意味着字段级撤销（基于 Journal 首事务的 old 值 / 快照）。

**裁决建议：采用"恢复 pre-ACM 状态"语义，修订 v2.0 §4.2 措辞**。理由：
1. 与"退出对等 / 零残留"（§9）、验收 #6 的可测表述一致——验收标准是硬约束，改语义就要改验收，代价更大；
2. 用户心智模型：`release` = "把我的机器还给我"，而非"留下投影、只卸责任"；若保留当前值，"解除与 VMR 的绑定"名不副实；
3. 实现上 Journal 已记录首事务 old 值，恢复成本低；
4. v2.0 §4.2 需补一句："先按 Journal 将受管字段回滚至 pre-ACM 值、移除 ACM 创建的字段；ACM 全新创建且无用户内容的文件整文件清理"。同时 v1.1 §7.5.2 同步修正（其表述当前偏向"保留"派）。
5. 注意：这是唯一一处建议"改 v2.0"的 A 级冲突——因为 v2.0 现有措辞与 v1.1 验收标准矛盾，且 v2.0 语义本身不够精确，属治理规格需澄清而非实现细节偏离。

## B 级：v1.1 内部不一致 / 与简化后的崩溃模型脱节

### B1. 崩溃恢复的"自动性"前后矛盾，多文件事务中途崩溃无机制支撑

| 位置 | 表述 |
|---|---|
| v1.1 §7.5.7 | 仅"启动时清理残留 `.acm_tmp`"；救砖靠用户手动 `rollback --hard` |
| v1.1 §7.5.1 阶段 3.5 | 异常回退只覆盖"**原子替换前**"的异常 |
| v1.1 §10.3 | 文案"↻ Recovered incomplete transaction … **file(s) restored from snapshot**"（自动恢复） |
| v1.1 §11.1 / §12 验收 #7 | "提交间隙 SIGKILL -> **重启后自动完成崩溃恢复**、配置回到事务前一致状态" |
| v1.1 §13 风险表 | "跨文件按序提交 + **内存字节回滚** + 崩溃恢复" |

**Gap 分析**：v1.1.1 去掉了 WAL 状态机（正确，符合 v2.0 §3.4 不变量 3），但**没有补上替代恢复规则**。Codex 是双文件事务（config.toml + auth.json），若在两次 `os.replace` 之间被 SIGKILL：journal 尚无该 txid 记录，但 snapshots/<txid>/ 已存在——当前 §7.5.7 对此沉默，验收 #7 却承诺自动恢复，机制与承诺脱节。

**建议**：补一条轻量恢复规则（不违反"无 WAL"原则）——**启动/doctor 时，若某 `<agent>` 存在快照目录 `<txid>` 而 journal 中无该 txid 的提交记录，则判定为未完结事务，从该快照原样还原受影响文件**。以此支撑验收 #7 与 §10.3 文案；"内存字节回滚"（风险表）措辞改为"快照还原"。v2.0 无需改动（其 §3.3 已含"写前落盘 snapshot"，此规则是其自然推论）。

### B2. `acm doctor` 检测项清单不一致且含过时项

- v2.0 §4.2：配置语法、引用缺失、漂移、权限异常（4 项）。
- v1.1 §10.1：另含"**未完结事务**、**进程冲突**、明文密钥告警"（7 项）。
- "进程冲突"随 A1 废除；"未完结事务"概念在简化模型下已弱化，应改为 B1 的"孤儿快照检测"（snapshot 有、journal 无）；"明文密钥告警"与 v2.0 §3.2"不持续骚扰告警"原则相容（doctor 属按需诊断，非骚扰），可保留。

**建议**：v1.1 §10.1 修订为：配置语法、文件权限、ENV 引用缺失、管理路径漂移、孤儿快照/未完结事务（按 B1 语义）、明文密钥提示。v2.0 的 4 项为语义级最小集，不冲突，无需改。

## 已核对、确认一致的项（无需处理）

- 状态机 6 枚举及优先级（SYNCED/OUT_OF_SYNC/DRIFTED/ERROR/UNMANAGED/NOT_DETECTED）
- 退出码规范（0/1/2/3/4/130）与 stdout/stderr 流约定
- Journal / Snapshot / Manifest 三元分工（Manifest 内存派生视图、快照 Append-only、快照命名 `<txid>`）
- Credential 引用规则（`${VAR}` 整字段替换、解析失败写前硬中止、明文合法 + 默认掩码）
- P0 = Claude Code + Codex + Pi，Aider 为 P1 首位
- Adapter 三职责（detect/config_paths/plan，verify 下沉金样门禁）、一切写入经 Safety Engine
- 漂移默认阻断、无自动修复路径；`use` 与 `apply` 语义分离
- 非破坏性两级承诺（语义级硬承诺 + 词法级 fixture 界定）
- 幂等 no-op 语义、跨 Agent 批处理独立成败原则
- 技术栈基线（Python 3.12+、TOML、PyPI/uvx 主路径、依赖预算）
- 铁律、Scope 边界、退出条件、成功标准（≤ 3 条命令、零手工编辑）

### A3 裁决评估（用户思路，采纳）

逻辑成立且优于原建议：将"解除托管"与"恢复原状"解耦--ACM 非侵入，摆脱 ACM 本就是零操作。两处补充已纳入：① 卸载指引应含删除 `~/.acm/`（journal/snapshots 留存含明文密钥的历史快照，是卫生与安全隐患）；② `release` 为写入命令，同样受漂移阻断规则约束（保持语义不变量 1 一致）。

### B1 裁决评估（用户思路，采纳）

逻辑成立。关键支撑：`os.replace` 保证单文件永不"写一半"，`apply` 幂等收敛使部分应用的 ChangeSet 下次执行自动补齐--自愈是免费副产品，无需新机制。因此承诺改写为三条零成本保证（而非全部删除），测试与验收相应改写，零新增复杂度。
