## 概述

在引入《ACM 配置管理范式、行业演进与终极架构深度剖析》（Deep Dive）的共识基准与核心诉求（P0 初始化便捷 > P1 安全防坏 > P2 开放扩展；双重所有权死锁；快照取证定位；状态物理隔离）后，我们对 `v2.0`（治理规格）与 `v1.1`（实现参考）之间的差异进行了全面重新审视与判定。

**总原则**：
- **v2.0 为治理性规格（Governing Spec）**，凡与 v2.0 原则、架构极简性（KISS/YAGNI）冲突的细节，**一律以 v2.0 为准，修改 v1.1 实现参考**。
- 拒绝过度工程（Over-engineering）：凡增加核心写入路径复杂度、引入双写一致性风险或引入重量级状态机的设计，一律予以剔除或简化。

## 一、实质性矛盾与关键分歧重新裁决

### M1：Manifest 存在形态——内存派生视图 vs 磁盘持久化文件

| 文档 / 来源 | 方案 |
|---|---|
| **v2.0 §3.3 & Deep Dive §5.1** | **内存派生视图（Derived View）**：从 Journal 事务历史与当前目标配置动态推导，**磁盘不单独双写 `manifest.json`**，消除双写一致性风险。 |
| **v1.1 §7.5.2 & §7.7** | 磁盘持久化文件：`~/.acm/state/<agent>/manifest.json`，存储 `current`、`pre_acm`、`created_by_acm` 等。 |

- **深度评估**：
  1. 过去曾误以为 `release` 命令必须依赖磁盘上的 `pre_acm` 原始值。但 Deep Dive §5.3（边缘场景 A）明确指出：`release` 的核心语义是**解除 ACM 托管并清空状态**，原位物理文件完整保留；若盲目恢复远古时期的 `pre_acm` 值反而会导致 Agent 因模型或端点废弃而启动崩溃。
  2. 对于 ACM 全新创建的文件（如 Pi 的 `models.json`），Journal 事务中已记录 `created=true` 与受管路径，通过内存推导即可精确判定是否需要 `unlink`。
  3. Journal 已是 state 区唯一的 Append-only 事务持久化 SSOT，额外维护磁盘 `manifest.json` 会引入经典的文件双写不一致与损坏风险。
- **裁决结论**：**以 v2.0 为准（内存派生视图）**。
- **修改建议**：更新 v1.1，将 `manifest.json` 从目录布局和写入流程中移除，改为运行时内存派生数据结构。

### M2：快照保留策略——Append-only 永久追加 vs FIFO × 20 自动清理

| 文档 / 来源 | 方案 |
|---|---|
| **v2.0 §3.3 & Deep Dive §4.4** | **Append-only 单纯追加留存**：写路径零轮转计算负担，全量留存以永久对齐 Journal 历史，不自动删除。 |
| **v1.1 §7.5.3** | 默认保留最近 20 份快照，FIFO 自动清理。 |

- **深度评估**：
  1. 配置变更是人类/工具的低频高价值决策，Agent 配置文件仅 5~20 KB，重度使用 5 年（10,000 次变更）总快照仅约 150 MB，磁盘占用微不足道。
  2. FIFO 自动轮转会在核心写入路径中引入目录遍历、配额排序与批量删除操作，增加故障面；更致命的是会破坏快照与 Journal 事务历史的 100% 对齐（导致用户回滚早期事务时快照丢失）。
  3. 若未来用户有清理诉求，仅通过显式命令（如 Phase 2+ 可选的 `acm clean`）主动触发，绝不在核心写路径中静默删文件。
- **裁决结论**：**以 v2.0 为准（Append-only 永久追加留存）**。
- **修改建议**：更新 v1.1 §7.5.3，废弃 FIFO 20 限制，改为单纯追加留存。

---

### M3：事务模型与崩溃恢复——原子替换 + 简单 Journal vs 重量级 WAL 状态机

| 文档 / 来源 | 方案 |
|---|---|
| **v2.0 §3.4 & Deep Dive §5.3** | **原子替换 + 写前快照**：排他写锁 + AST 修改 + 写前 Snapshot 留存 + `os.replace` 原子替换，消除沉重的 WAL/2PC 中间状态机。 |
| **v1.1 §7.5.1 & §7.5.7** | 三阶段提交 + 显式状态机（`PREPARED → COMMITTING → COMMITTED / ABORTED`）+ 崩溃恢复检查。 |

- **深度评估**：
  1. 单机 CLI 场景下单次写入仅耗时 5~20 毫秒。POSIX / Windows 的 `os.replace` 在文件系统层是原子操作（< 2ms），天然不存在“目标文件写入一半损坏”的中间态。
  2. 在写前已单向落盘了 Snapshot，即使进程在极罕见的瞬间被 SIGKILL，原文件要么完全未变，要么已完全替换为新文件。
  3. 人为构造 `COMMITTING` 状态与启动检查反而增加了状态管理的复杂度和脆弱性。
- **裁决结论**：**以 v2.0 为准（无沉重 WAL 状态机）**。
- **修改建议**：v1.1 中的三阶段提交简化为：`写前 Snapshot -> AST 内存修改 -> os.replace 原子写回 -> Append Journal`，去除多余的中间悬挂态。

### M4：Agent 状态枚举——6 种主状态 vs 7 种（含 CONFLICT）

| 文档 | 状态枚举 |
|---|---|
| **v2.0 §4.1** | `SYNCED \| OUT_OF_SYNC \| DRIFTED \| ERROR \| UNMANAGED \| NOT_DETECTED`（6 种） |
| **v1.1 §7.6** | 上述 6 种 + `CONFLICT`（进程冲突/锁冲突） |

- **深度评估**：
  1. 状态机枚举应当唯一表征**落盘配置的真实对齐情况**。
  2. 写锁冲突或进程冲突是**运行时的临时阻断条件**，通过命令执行时的退出码 2（安全阻断）与 stderr 告警实时体现，不应固化为 Agent 配置本身的持久主状态。
- **裁决结论**：**以 v2.0 为准（6 种主状态）**。
- **修改建议**：v1.1 §7.6 移除 `CONFLICT` 状态枚举，明确冲突属于运行时执行阻断（Exit Code 2）。

### M5：Adapter Protocol——3 个纯粹职责 vs 4 个方法（含 verify）

| 文档 | Adapter Protocol 契约 |
|---|---|
| **v2.0 §5 & Deep Dive §7.2** | **detect / config_paths / plan**（运行时彻底零 I/O，纯函数编译器） |
| **v1.1 §7.4** | detect / config_paths / plan / **verify** |

- **深度评估**：
  1. Adapter 应保持为极致精简的纯函数模块（输入 Profile，输出 ChangeSet），不应在运行时承担冗余的文件读取与断言校验。
  2. 校验与保真能力 100% 下沉到开发期的**金样测试套件（Golden Fixture Suite）**与 CI 门禁中。
- **裁决结论**：**以 v2.0 为准（3 个方法）**。
- **修改建议**：v1.1 将 `verify()` 从 Adapter Protocol 运行时契约中移除，保留相关断言逻辑用于单元测试套件。

### M6：退出码定义——3 码粗粒度 vs 5 码精细化

| 文档 | 退出码定义 |
|---|---|
| **v2.0 §4.3** | `0`=成功/no-op；`1`=错误；`2`=安全阻断 |
| **v1.1 §10.2** | `0`=成功；`1`=配置错误；`2`=安全阻断；`3`=I/O失败；`4`=未找到；`130`=SIGINT |

- **深度评估**：
  1. Deep Dive §1 P0 诉求强调“可脚本化与 CLI 一等公民”。
  2. 在自动化脚本与 CI 集成中，区分配置错误（1）、安全阻断（2）、I/O 故障（3）和未找到目标（4）具有明确的实用价值，符合 Unix CLI 标准实践，且不增加架构复杂度。
- **裁决结论**：**以 v1.1 的 5 码规范为准**。
- **修改建议**：在 v2.0 §4.3 补充细化退出码 3/4/130。

### M7：Credential 明文处理与告警频率

| 文档 | 明文密钥策略 |
|---|---|
| **v2.0 §3.2 & Deep Dive §6.3** | 单机合法选择；CLI 输出默认掩码；**仅在团队共享配置（Git）或权限异常时提示/阻断**，不持续骚扰告警。 |
| **v1.1 §7.3.1** | 明文存储为 escape hatch，`acm doctor` 持续告警。 |

- **深度评估**：
  1. 许多单机开发者直接手写明文 key 是常见合法诉求，频繁且不可关闭的告警会破坏 CLI 体验。
  2. 安全红线应设在“团队共享 Git 仓库”（禁止明文）与“文件系统权限未达 0700/0600”之时。
- **裁决结论**：**以 v2.0 为准**。
- **修改建议**：v1.1 §7.3.1 改为“仅在权限异常或共享场景下提示”。

## 二、Gap 与细节歧义清理

| 编号 | 差异项 | 现存状态 | 新裁决与建议 |
|---|---|---|---|
| **G1** | 快照路径命名 | v2.0 用 `snapshots/<txid>/`，v1.1 部分用 `snapshots/<ts>/` | **统一为 `<txid>`**。与 Journal 主键精确绑定，方便 `rollback --to-tx` 索引。 |
| **G2** | 进程守护实现 | v1.1 详细列出 BLOCK/WARN 分级，v2.0 简化淡化 | **以 v2.0 原则为主**：依赖排他写锁与 AST 保护，进程检测仅通过标准库作为辅助性 WARN 提示，不引入高误判的外部进程阻断。 |
| **G3** | `acm diff` 的 UNMANAGED 行为 | v1.1 规定了 Dry-run 虚拟比对，v2.0 未展开 | **采纳 v1.1 细节**。未接管 Agent 运行 diff 时展示预期变更，对用户体验极佳。 |
| **G4** | 动态适配器热加载表格标记 | v1.1 §6 D2 表格中未标注 Phase 2 | **修正 v1.1**。在 D2 表格适配器格子中注明 `(Phase 2)`，避免与 D7 冲突。 |
