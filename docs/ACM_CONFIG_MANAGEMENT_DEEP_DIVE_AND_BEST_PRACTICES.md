## 1. 共识基准与核心诉求对齐

在展开技术讨论之前，我们首先明确并固化以下四个已被你明确确认的基准共识：

```
┌───────────────────────────────────────────────────────────────────────────┐
│                           ACM 核心目标优先级金字塔                          │
├───────────────────────────────────────────────────────────────────────────┤
│  P0 (第一优先): 初始化便捷性                                              │
│     • 一键把本机多个 Agent 指向统一的模型/Provider（如 VMR/虚拟模型/官方 API）    │
│     • 零手动编辑、≤ 3 条命令、零门槛开箱即用                              │
├───────────────────────────────────────────────────────────────────────────┤
│  P1 (第二优先): 安全防坏与可逆性                                          │
│     • 切换 Profile 或回滚时，绝不搞坏 Agent 宿主已有的其他配置               │
│     • 精确的字段级逆操作 + 强力快照安全兜底                                │
├───────────────────────────────────────────────────────────────────────────┤
│  P2 (第三优先): 开放插件化与社区扩展                                      │
│     • 支持 Claude Code, Codex, Pi, OpenClaw 等；能低成本接入新 Agent       │
├───────────────────────────────────────────────────────────────────────────┤
│  P3 (权衡取舍): 其余复杂度一律让步                                        │
│     • 不做 Agent 全生命周期管理，不侵入私有 DB，不承担通用 Secret Storage  │
└───────────────────────────────────────────────────────────────────────────┘
```

* **状态与文件物理隔离原则**：第三方软件的目标配置文件（如 `~/.claude/settings.json`、`~/.codex/config.toml`）仅作为**“最终生效状态的物理受体”**；ACM 的版本历史、事务日志、所有权清单、整文件快照完全存放于 ACM 独立的工作区（`~/.acm/state/`）。
* **快照定位澄清**：对第三方文件的完整快照，其核心定位是**“只读审计证据（Audit Forensics）与灾难恢复（Disaster Recovery）”**，而不是为了去管理 Agent 自身的会话、Token 统计或 UI 状态。
* **演进路径明确**：单机 CLI 为第一步基础；团队共享通过“Git 托管 SSOT + 个人 Overlay 覆盖”实现，无需重写架构。

## 2. 深度剖析：配置管理领域“最常犯的错误”与 40 年演进史

你在追问中提到想更深入理解*“人类处理这类问题时常犯的一个错误以及反复验证的教训”*。这背后的历史与技术哲学非常值得深入复盘。

### 2.1 为什么把“原位第三方文件”当“版本数据库”必然崩溃？

所谓“最常犯的错误”，简单用一句话概括就是：
> **“试图在一个由第三方软件主导生命周期、且存在外部异步写入的原位物理文件（In-place File）上，构建一套属于自己的精密版本控制系统。”**

为什么很多人会本能地想这么做？
因为在开发者的直觉里：“这个文件既然在我的磁盘上，我只要在每次改动时 diff 一下、记一个 version、打一个 patch，不就完全可控了吗？”

然而，现实中这个物理文件**同时受两个权力实体的支配**：
1. **你的工具（ACM）**：希望它是一张干净的画布，严格按照你的意图进行版本演进。
2. **宿主软件（Agent 运行时）**：它也是这个文件的写作者。当它运行时，它会随时向这个文件写入当前窗口大小、最近会话 ID、授权 Token、插件更新时间戳，甚至会在软件升级时自动将 JSON 缩进从 2 空格改成 4 空格、将 TOML 表重排、把用户的注释全量抹掉。

一旦你试图在原位文件上做全量版本控制，你就会遇到不可调和的**双向控制权死锁（Dual-Authority Deadlock）**：
* 你的工具把文件恢复到版本 $V_1$，结果把 Agent 刚才偷偷写进去的重要会话 ID 抹掉了；
* Agent 软件升级重构了文件结构，导致你记录的字段 patch 路径全部失效。

为了解决这个问题，整个软件工程界在过去 40 年里经历了四个清晰的演进阶段：

```
                ┌────────────────────────────────────────────────────────┐
                │             配置管理 40 年核心演进路径                  │
                └────────────────────────────────────────────────────────┘
                                            │
   ┌────────────────────┬───────────────────┴───────────────────┬────────────────────┐
   ▼                    ▼                                       ▼                    ▼
【阶段 1: 模板覆写】   【阶段 2: 不可变派生】                 【阶段 3: 字段所有权】 【阶段 4: 现代 Dotfiles】
• Puppet / Chef      • Nix / Guix / Docker                  • K8s Server-Side    • Chezmoi / Home-Mgr
• 原位文件直接覆盖   • 彻底废弃原地修改                     • 明确每个字段的属主 • 模版编译 + 局部感知
• 缺点: 外部修改抹除 • 机制: 只读 Store + 软链             • 机制: FieldManager • 机制: 独立 SSOT + 投影
```

---

### 2.2 阶段一：原位模版覆盖时代（Puppet / Chef / CFEngine）的血泪教训

* **机制**：在 2000–2010 年代，运维自动化工具通过 Jinja2 或 ERB 模版，直接将配置全量渲染并覆盖到操作系统的 `/etc/nginx/nginx.conf` 等原位文件上。
* **致命痛点（Configuration Drift 地狱）**：
  * 如果管理员在机器上手工调了一个参数，下次 Puppet 执行时会**静默覆盖**管理员的修改，导致故障被覆盖；
  * 如果 Puppet 试图通过复杂的正则或 `sed` 去原位替换某几行，随着目标软件版本升级，脚本就会频繁把文件改坏。
* **教训**：**全量覆写会扼杀局部自由；纯正则/文本行替换会摧毁文件语法。**

---

### 2.3 阶段二：不可变派生时代（Nix / Guix / Container）的降维打击

* **机制**：2010 年代后，NixOS 和容器技术提出了彻底的范式转移：**绝不修改任何原位文件**。
  * 所有的配置都是输入参数，经过纯函数编译，输出到只读的哈希目录（如 `/nix/store/a8f9...-config`）；
  * 最终目标文件只是指向这个只读目录的一个**符号链接（Symlink）**；
  * 要回滚？只需把软链接指向上一份不可变哈希目录，1 毫秒实现原子回滚。
* **启示**：把“生成逻辑”与“宿主消费”彻底解耦。但它的缺点是：**宿主软件必须是纯只读消费配置的**。如果宿主软件（如 Claude Code）必须在运行中往自己的配置文件里回写状态，纯软链接就会被宿主软件打断（许多软件在保存时会删除旧文件新建新文件，从而破坏软链接）。

---

### 2.4 阶段三：多方字段所有权时代（Kubernetes Server-Side Apply）的终极解法

* **机制**：当多个控制器、管理员、Helm 都要同时修改同一个 YAML 对象时，Kubernetes 诞生了 **Server-Side Apply (SSA)** 与 **字段所有权机制（Field Management）**。
  * 系统为每个资源对象维护一份隐藏的元数据 `managedFields`；
  * 它详细记录了：`spec.replicas` 是由 HPA（弹性伸缩器）拥有的；`spec.template.spec.containers[0].image` 是由 CI 流程拥有的；`metadata.labels` 是由 Helm 拥有的；
  * 任何一方发起修改时，**只校验自己拥有的字段**。如果 Helm 试图去改 HPA 拥有的 `replicas`，系统会直接报错提示冲突（Conflict），除非显式声明 `--force-conflicts`（强行转移所有权）。
* **对 ACM 的重大价值**：**这正是 ACM 字段所有权感知与 AST Surgical Patching 的直接理论来源！**
  * ACM 明确声明：“我只拥有 `model`、`base_url`、`api_key` 这几个 JSON/TOML 路径的所有权”；
  * 对于非 ACM 拥有的字段（如 `permissions`、`plugins`），ACM 承认其所有权属于 Agent 宿主或用户，在语义上绝对不予触碰。

---

### 2.5 阶段四：现代 Dotfiles 治理范式（Chezmoi vs Mackup vs Home-Manager）

在开发者个人配置管理领域：
* **Mackup（早期）**：直接把 `~/.config` 软链到 Dropbox/Git。**极易因为多台机器环境差异把配置同步搞崩**。
* **Chezmoi（现代标杆）**：
  * 在 `~/.local/share/chezmoi` 维护单一 SSOT；
  * 通过 Go template 渲染；
  * 采用 `chezmoi diff` 显式查看差异；
  * 遇到外部手动修改时，提供三路合并（3-Way Merge），绝不无脑覆盖。
* **ACM 的定位**：ACM 可以被理解为**“专为 Coding Agent 模型连接层量身定制的、具备字段级所有权感知与安全防护的智能 Chezmoi”**。

## 3. 维度对比：非结构化 Markdown vs 结构化配置的本质鸿沟

你提到之前管理 Agent 定义（Identity、Soul、Tools 的 Markdown 文档）时，核心原语是 `Backup -> Diff -> Deploy`（覆盖 / 不覆盖），运转得很顺畅。那么，为什么到了 YAML、JSON、TOML 结构化配置时，复杂度会呈几何级数上升？

```
                ┌────────────────────────────────────────────────────────┐
                │          Markdown 文本 vs 结构化配置的核心差异          │
                └────────────────────────────────────────────────────────┘
                                            │
                 ┌──────────────────────────┴──────────────────────────┐
                 ▼                                                     ▼
    【Markdown Agent 定义文件】                           【JSON / TOML / YAML 配置文件】
• 语义形态: 纯文本流 / 自然语言                          • 语义形态: 强类型树状数据结构 (AST)
• 归属权: 100% 属于作者本人                               • 归属权: 多方共享 (ACM + Agent 运行时 + 用户手写)
• 操作粒度: 整文件 / 章节级替换                           • 操作粒度: 精确到键值路径 (如 env.BASE_URL)
• 破坏容忍度: 语法容错极高 (多空行无所谓)                 • 破坏容忍度: 语法容错为零 (缺逗号/缩进错即崩溃)
• 运行时并发: 外部无自动回写进程                          • 运行时并发: Agent 进程持续在后台读写
```

### 3.1 文本级覆盖（Identity / Soul / Tools）的简单性本质

1. **单一写者（Single-Writer）**：这些 Markdown 文件的内容完全由你（或你的编排系统）决定，底层的 Agent 进程在运行时绝不会擅自修改你的 `Soul.md` 或在里面追加一行私有数据。
2. **文本级整体性（Coarse-Grained Cohesion）**：Prompt 的逻辑是一个整体，覆盖就是全新版本，不覆盖就是保留旧版，不存在“我只想更新 Soul 的第二段，但必须把 Agent 刚才在第三段写的状态保留下来”这种双向合并需求。
3. **极高的语法容错度**：多一个换行、少一个空格、缩进不一致，完全不影响 LLM 解析 Prompt。

---

### 3.2 结构化 AST 级修改（JSON/YAML/TOML/JSONC）的三大死穴

而对于 Agent 的配置文件（如 `settings.json`、`config.toml`、`.aider.conf.yml`），情况发生了根本性突变：

#### 死穴 1：词法保真度问题（Lexical Fidelity & Formatting Loss）
* 标准的 Python `json.dumps()` 或 `yaml.dump()` 只是**序列化器（Serializer）**，不是**保真编辑器（Round-trip Editor）**。
* 如果你用标准库 `json.load()` 读取了 Codex 的 `config.toml`，然后再写回：
  * 用户手写的注释会被全部抹杀；
  * 所有的 key 顺序会被打乱；
  * 缩进可能从 2 空格变成 4 空格；
  * 这种破坏虽然在数据语义上等价，但在用户体验和 Git Diff 上是不可接受的灾难。
* **解法**：必须引入 `tomlkit`、`ruamel.yaml` 以及专用保序 JSON 编辑器，以 AST 树形式修改目标节点，未修改的文本原样保留。

#### 死穴 2：Schema 双向异构与隐式升级（Schema Drift）
* Markdown 的语法是 Markdown 规范（40 年不变）；
* 但 Claude Code、Codex、Pi 等 Agent 几乎每个月都在迭代发布新版本：
  * 今天字段叫 `effortLevel`，明天可能改成 `thinking.effort`；
  * 今天配置放在 `~/.codex/config.toml`，明天可能迁移到 `~/.config/codex/`。
* 任何结构化字段操作都面临上游 Schema 突变导致路径失效的风险。

#### 死穴 3：运行时异步交织写入（Concurrent Asynchronous Mutation）
* 当你敲下 `acm use` 的瞬间，后台开着的 Claude Code 进程可能恰好刚刚完成了一次会话，正准备把最新的 OAuth token 或会话记录写入 `settings.json`。
* 此时如果不做并发保护与语义级三路合并，就会发生经典的文件覆盖丢数据问题。

---

### 3.3 从“文本替换（Text Deploy）”跨越到“AST 外科手术（Surgical Patching）”

因此，从管理 Markdown 跨越到管理结构化配置，ACM 必须完成从**“文件搬运工”**到**“AST 外科手术医生”**的进化：

```python
# 传统的 Markdown 部署模型（文件级）
def deploy_markdown(src_file, dst_file, overwrite=True):
    if not dst_file.exists() or overwrite:
        dst_file.write_text(src_file.read_text())  # 简单粗暴，完全成立


# ACM 的结构化配置部署模型（AST 字段级）
def apply_structured_config(target_file, changeset: ChangeSet):
    ast = parse_roundtrip(target_file)  # 保持注释与排版
    for op in changeset.ops:
        ast.set_path(op.path, op.new_value)  # 仅精确改动指定 AST 节点
    atomic_write(target_file, ast.to_string())  # 原子落盘
```

## 4. 核心问题回答：全量配置可控性、历史追溯与任意切片植入

基于上述历史教训与结构化配置的本质，现在我们可以严谨、系统地回答你的四个核心疑问。

### 4.1 “完全可控”在理论与现实中的真实边界在哪里？

* **理论边界（不可能三角）**：
  在计算机科学中，你不可能同时做到以下三点：
  1. 允许第三方软件在任意时刻自由修改该文件（宿主自由度）；
  2. 只修改其中的个别字段，不控制其他字段（局部非侵入性）；
  3. 对该文件的所有历史状态实现 100% 确定性的全局时光机复原（全局强一致性）。
* **现实边界（ACM 的最优解）**：
  ACM 的“完全可控”必须界定在：
  * **对“受管字段（Managed Fields）”实现 100% 绝对可控**（确定性投影、精确值追踪、无歧义回滚、漂移阻断）；
  * **对“未受管内容（Unmanaged Content）”实现 100% 零破坏保障 + 只读快照证据留存**。

```
                     ┌──────────────────────────────────────┐
                     │          ACM 配置可控性边界划分        │
                     └──────────────────────────────────────┘
                                        │
           ┌────────────────────────────┴────────────────────────────┐
           ▼                                                         ▼
【ACM 强力控制区 (Managed Keys)】                          【宿主自治保护区 (Unmanaged Keys)】
• base_url, api_key, model, reasoning                   • permissions, hooks, plugins, history
• 100% 确定性写入、幂等收敛                              • 绝对零破坏保留 (AST 解析树 diff 保护)
• 字段级逆操作回滚 (Journal Tx)                           • 仅做只读审计快照留存 (Audit Snapshot)
• 外部修改视为 Drift 触发安全阻断                         • 允许外部自由修改，不误报 Drift
```

### 4.2 历史版本叠加与时间线穿梭（Time-Travel）的科学实现机制

要做到像 Git 一样能够叠加很多版本、回溯历史，但粒度又是“字段切片”，行业内的最佳方案是**“事件溯源日志（Event Sourcing / Journaling）”**。

这正是 ACM 在 `~/.acm/state/<agent>/journal.jsonl` 中设计的架构：
1. **每一个写操作都是一个不可变事件（Transaction Event）**：
   ```json
   {
     "txid": "tx-20260818-001",
     "timestamp": "2026-08-18T10:00:00Z",
     "profile": "daily",
     "ops": [
       {"path": "env.ANTHROPIC_BASE_URL", "old": "https://api.anthropic.com", "new": "http://127.0.0.1:8800/v1", "created": false},
       {"path": "model", "old": "claude-3-5-sonnet-20241022", "new": "vmr/coding", "created": false}
     ]
   }
   ```
2. **快照式字段还原（Direct Field Restoration）——拒绝脆弱的链式逆向推演**：
   * 要回滚到历史事务 $Tx_k$，系统无需运行脆弱复杂的“从 $Tx_n$ 逐级逆序推演回放引擎（Reverse Replay Engine）”；
   * 核心逻辑极其质朴：直接从 Journal 中提取 $Tx_k$ 记录的目标字段历史值（或接管前原始值），通过 AST 外科手术将这几个受管键直接设回目标值，并作为一次新的 Apply 事务原子落盘；
   * 在还原过程中，目标文件中的未管理数据（如 Agent 期间写入的会话 ID）在 AST 中**毫发无损**，且彻底消除了中间多版本回放导致的状态崩溃风险。

### 4.3 任意指定配置切片的动态植入（Selective Injection / Cherry-pick）

如果你希望做到“只把某几个特定的配置信息（例如只植入 reasoning 参数，或者只更新 proxy 设置）单独植入到某个 Agent”：
* **理论实现路径**：
  1. 在 Core Config 中支持模块化声明（如 `[snippets.proxy]` 或 `[snippets.reasoning]`）；
  2. Adapter 的 `plan()` 函数接收这个切片，生成仅包含该切片路径的局部 `ChangeSet`；
  3. Safety Engine 将这个微型 `ChangeSet` 通过三阶段提交精准打入目标文件 AST。
* **架构定位与 MVP 边界（防 Scope Creep）**：
  - **理论完备性证明**：基于 AST 的 `ChangeSet` 架构在数学上天然支持任意粒度的切片植入（Partial Patching）。
  - **MVP 严格约束**：在 Phase 1 (MVP) 中，ACM 严格坚守 Spec v2.0 的极简原则（全局单一激活 Profile），**不引入 `snippets` 配置 DSL 或局部 Cherry-pick 命令**，避免过早优化带来的认知与配置膨胀；底层 `Adapter.plan()` 契约保持纯函数与局部变更生成能力，为未来演进平滑预留空间。

### 4.4 未管理数据的完整快照（Audit Snapshots）最佳实践：保留什么、保留多久、如何比对？

你提到：*“其他的信息呢？我们是不是也应该把它保留下来一个快照呢？以便做对比。它的背后的核心逻辑是我能够作为一个审计证据，仅此而已。”*

这个思路**完全正确且非常专业**。在配置工程中，这被称为 **“安全网（Safety Net）与取证快照（Forensic Snapshot）”**。

```
                       ┌────────────────────────────────────────┐
                       │       审计快照生命周期与存储最佳实践     │
                       └────────────────────────────────────────┘
                                           │
         ┌─────────────────────────────────┼─────────────────────────────────┐
         ▼                                 ▼                                 ▼
   【触发时机与捕获】                 【存储与保留策略】                【审计比对与消费】
• 每次写入命令 (use/apply) 执行前   • 路径: state/<agent>/snapshots/  • acm diff --against-snapshot
• 在阶段 1 物理修改前整文件备份     • 全量追加保留 (Append-Only)       • 发生未决故障时 doctor 诊断比对
• 原样保留原始字节 (Raw Bytes)      • 目录权限 0700 (含敏感凭据保护)   • acm rollback --hard 灾难恢复
```

#### 关键设计规范：
1. **保留什么？**
   * **原样字节流备份（Raw Byte Stream）**：不要做任何过滤或重排，原汁原味地备份目标文件在 ACM 动刀前那一刻的字节流。包括文件的最后修改时间（mtime）和权限模式。
2. **保留多久（Retention Policy）？——为什么坚决废弃“自动轮转”，采用“全量追加保留（Append-Only Forever）”**
   * **范式纠偏（拒绝把低频配置当高吞吐日志）**：
     “FIFO 轮转 / 定期清理”来源于高并发日志系统（每天产生数百 GB 日志）。但配置变更本质是**低频、高价值的人类/工具决策**（正常使用一年仅几十到数百次）。
   * **磁盘占用微不足道（量化推演）**：
     Agent 目标配置文件通常仅 5~20 KB。连续极重度使用 5 年（变更 10,000 次），快照总大小仅约 **150 MB**（甚至不及一个普通的前端 `node_modules`）。为省十几 MB 空间去搞轮转是典型的过度工程。
   * **保持三元历史 100% 永久对齐**：
     Journal 是 Append-only 的事务日志。若快照被自动裁剪，会导致用户回滚到早期事务时报错“快照已被删除”，破坏系统一致性与公理 3（可逆性）。
   * **核心写路径零额外故障面**：
     写快照仅需单向 `write_bytes()`，无需扫描目录、排序、计算配额与批量删除，消除并发死锁与权限异常风险。
   * **显式维护策略**：
     绝不在 `use` / `apply` 核心写入路径中静默删文件；若未来用户有强迫症清理诉求，仅通过显式命令（如 Phase 2+ 可选的 `acm clean`）由用户主动触发。
3. **如何比对（Diffing）？**
   * 提供专用审计命令：`acm diff <agent> --against-snapshot`；
   * 在 CLI 输出中，将变更分为两栏：**[ACM 管理的字段变动]** 与 **[外部/宿主自行发生的变动]**，让用户一眼看清是 ACM 动了配置，还是宿主软件自己修改了内容。

## 5. ACM 当前架构健壮性全面评估与防御加固

基于你的核心目标（初始化便捷 > 安全防坏 > 插件扩展），我们对 ACM 现有的设计进行一次严肃的架构健壮性审计。

### 5.1 当前轻量状态体系（Journal + Snapshot + 内存 Manifest）的健壮性判定

**判定结论：摒弃冗余的磁盘多写，保留 Journal 与 Snapshot 作为状态基石，兼顾极致简单与可逆性。**

| 组件 | 物理位置 | 核心职责 | 为什么缺一不可？ |
|---|---|---|---|
| **Journal** | `~/.acm/state/<agent>/journal.jsonl` | Append-only 事务事件历史（记录每次 ChangeSet、txid、时间戳、ops 变更） | **解决“字段级精准回滚与所有权推导”**：作为 state 目录唯一的持久化事务 SSOT，回滚时不破坏 Agent 后来写的新状态。 |
| **Snapshot** | `~/.acm/state/<agent>/snapshots/<txid>/` | 物理文件的整文件原始字节备份（Append-only，单纯追加留存） | **解决“灾难级兜底（Disaster Recovery）与取证”**：写前瞬间备份，提供 `--hard` 一键复原通道，写路径零轮转计算负担。 |
| **Manifest** | *(内存派生视图)* | 运行时动态推导字段所有权与当前值 | **消除磁盘状态双写**：无需在磁盘额外持久化 `manifest.json`，由 Journal 与当前文件内容动态求值，消除双写一致性风险。 |

---

### 5.2 为什么“排他写锁 + AST 字段保留”是单机并发与防篡改的最优解？

在单机 CLI 场景下，单次配置写入仅耗时 **5~20 毫秒**。无需引入分布式数据库复杂的“多层指纹提交”或“SSA 冲突协议”，ACM 采用质朴而极其稳健的**“写锁 + AST 精确字段注入 + 原子写回”**流水线：

```
[ACM 写入流水线 (use / apply)]
       │
       ▼
1. 获取全局排他写锁 (Global File Lock)
       │
       ▼
2. 读入目标文件并解析为 AST 树 (保留所有注释、键序与未管字段)
       │
       ├── 校验受管字段: 若 ACM 管理的字段被外部手动篡改 ──> [阻断并报 Drift 告警]
       │
       └── 校验通过: 仅将 ChangeSet 中的受管字段更新到 AST 节点 (未管字段保持原样)
       │
       ▼
3. 原子替换写回 (tempfile.write + os.replace)
       │
       ▼
4. 释放写锁
```

这套机制返璞归真：
1. **写锁消除了 TOCTOU 竞争**：防止多个进程同时修改目标配置；
2. **AST 天然保护未管理字段**：外部 Agent 写入的会话状态、插件信息在 AST 中根本不被触碰，写回时原样保留；
3. **零额外分支开销**：消除虚浮的哈希分流机制，逻辑线性透明。

### 5.3 极端边缘场景分析与防御措施（Edge Cases & Defenses）

为了确保系统达到工业级稳健，ACM 针对以下三大极端场景设立了明确的防御底线：

#### 边缘场景 A：用户在 `acm release` 时释放 Agent 托管
* **隐患**：若盲目恢复远古时期的 pre-ACM 初始值，会导致 Agent 因模型或端点早已废弃而启动崩溃。
* **防御机制**：
  1. **解除托管原则**：`release` 的核心语义是“停止管理该 Agent”，清除 ACM 状态记录，原位物理文件完整保留；
  2. **ACM 新建文件清理（`created=true`，如 `models.json`）**：`release` 时若发现该文件由 ACM 新建且不包含任何非 ACM 管理的键，执行整文件 `unlink`；若包含用户手写内容，则保留文件并剔除受管字段。

#### 边缘场景 B：Agent 在新机器上初次运行，配置父目录尚不存在
* **隐患**：`~/.pi/agent/` 目录尚未生成，写临时文件引发 `FileNotFoundError`。
* **防御机制**：原子写执行器统一封装 `target.parent.mkdir(parents=True, exist_ok=True)`。

#### 边缘场景 C：ACM 写入过程中遭遇断电或进程中断
* **隐患**：文件写入中断导致损坏。
* **防御机制（原子替换自然免疫）**：
  1. **写前 Snapshot 留存**：在动刀前完成单向备份，永远拥有最后一份未篡改底板；
  2. **POSIX/Win 原子重命名（Atomic `os.replace`）**：新内容先完整写入同目录临时文件，再通过 `os.replace` 瞬间替换（< 2ms），文件系统层面不存在“写入一半”的中间损坏态；
  3. **消除冗余 WAL 状态机**：无需实现沉重的 `COMMITTING`/`fsync` 二阶段事务协议，避免人为构造“悬挂中间态”，保持系统极致精简与自洽。

## 6. 极简团队协作扩展模型（Team SSOT + Personal Overlay）

你提出的团队扩展设想非常敏锐：
> *“把我们的 Single source of truth (SSOT) 核心配置作为 Git repo 放到版本服务器上，我们的脚本自动加载这个 SSOT……如果有必要的话，个人版配置可以作为团队版的补充，个人覆盖团队版。”*

这是一个**极其经典且复杂度极低（Near-Zero Complexity）**的架构模式。在业界，这被称为 **“分层配置级联（Hierarchical Cascading Configuration）”**。

```
                ┌────────────────────────────────────────────────────────┐
                │          团队 SSOT + 个人 Overlay 配置级联架构          │
                └────────────────────────────────────────────────────────┘
                                            │
        ┌───────────────────────────────────┴───────────────────────────────────┐
        ▼                                                                       ▼
【团队级共享 SSOT (Git 托管)】                                         【个人级本地配置 (Local)】
• 来源: 团队 git clone 到本地 / 远程 URL                              • 来源: ~/.acm/config.toml
• 内容: 官方 Provider 端点、共享 VMR 路由、基准模型规范              • 内容: 个人私有 API Key、本地 Ollama 模型、调试 Profile
• 权限: 团队统一维护、只读同步                                         • 权限: 开发者自由手写
                                            │
                                            ▼
                           ┌─────────────────────────────────┐
                           │   ACM 内存层级联合并器 (Merge)   │
                           │   (Personal 优先覆盖 Team)      │
                           └─────────────────────────────────┘
                                            │
                                            ▼
                           ┌─────────────────────────────────┐
                           │      最终 ResolvedProfile       │
                           │   (用于投影到本地各 Coding Agent) │
                           └─────────────────────────────────┘
```

### 6.1 极简实现方案（无需改造现有 Safety Engine）

1. **配置文件加载顺序**：
   * Base 层（团队）：`~/.acm/team_config.toml`（可以通过 Git 自动拉取更新）；
   * Override 层（个人）：`~/.acm/config.toml`（个人本地文件）。
2. **字典深度合并算法（Deep Merge）**：
   $$\text{FinalConfig} = \text{Merge}(\text{BaseTeamConfig}, \text{PersonalConfig})$$
   * 若团队定义了 `[providers.vmr]`，个人也定义了 `[providers.vmr]`，则个人的 `api_key` 或 `base_url` 覆盖团队值；
   * 若团队新增了 `[models.coding]`，个人没有定义，则直接继承团队模型；
   * 若个人新增了 `[models.my_local]`，则并入模型列表。
3. **凭据安全隔离（Credential Cleanliness）**：
   * 团队 Git 仓库里的 TOML 只写环境变量引用（如 `api_key = "${TEAM_VMR_KEY}"`）；
   * 团队仓库中**永远不出现真实明文密钥**，每个开发者只需在自己的 `.zshrc` / `.bashrc` 中注入环境变量即可完成认证。

这一设计无需引入任何分布式数据库或复杂协同协议，完全复用单机 CLI 现有的三阶段提交与适配器流水线。

### 7.1 为什么普通 Python 模块是最好的 Adapter 载体？

* **拒绝自定义 DSL / JSON 规则模版**：
  许多项目试图设计一套 JSON Schema 或 YAML 规则来描述配置映射，但很快就会发现：每家 Agent 的配置怪癖完全不可预测（例如 Claude Code 需要把配置塞进 `env` 字典，Codex 需要把 model 放在顶层同时写 `auth.json`，Pi 还要做方言转换）。
* **坚持“适配器即 Python 代码”**：
  一个适配器就是一个标准 Python 文件（约 50–100 行代码），实现 3 个纯粹方法。任何开发者只要懂 Python 就可以在半小时内写出一个新 Agent 的适配器。

### 7.2 适配器标准生命周期契约

```python
from typing import Protocol
from pathlib import Path
from acm.core.models import ResolvedProfile, ChangeSet


class Adapter(Protocol):
    agent_id: str
    display_name: str

    def detect(self) -> bool:
        """1. 探测本机是否安装了该 Agent"""
        ...

    def config_paths(self) -> list[Path]:
        """2. 声明涉及的目标物理文件（供 Safety Engine 统一加锁、备份快照与落盘）"""
        ...

    def plan(self, profile: ResolvedProfile) -> ChangeSet:
        """3. 纯函数：将通用 Profile 转译为目标 Agent 的 AST 字段修改集（100% 内存纯运算，不碰物理 I/O）"""
        ...
```

> **核心设计收益（零运行时 I/O 负担）**：
> Adapter 彻底成为 **纯函数编译器（Profile → ChangeSet）**，不授予物理写盘权限，也不承担运行时的冗余读取校验（`verify`）；
> 校验职责 100% 下沉至开发期的 **金样测试套件（Golden Fixtures）** 与 CI 门禁，线上写路径极致轻量高速。

### 7.3 金样测试套件（Golden Fixture Suite）作为社区准入门槛

社区贡献适配器时，如何保证不搞坏用户的配置？
**强制要求随 PR 提供金样测试用例（Golden Fixture Suite）**：
1. **输入样本**：提供一份该 Agent 官方生成的真实配置文件（带手写注释、带非管理字段、带格式缩进）；
2. **正向三步自动化断言**：
   * **Apply 断言**：ACM 写入后，目标字段值完全符合预期；
   * **Non-destructive 断言**：未管理节点语义 100% 不变，注释和排版完好无损；
   * **Rollback 断言**：回滚后恢复原状，且在 Apply 与 Rollback 之间模拟注入的外部状态完全存活。
* 只要金样测试全绿，社区贡献的适配器就可以安全并入主干。

### 7.4 上游 Schema 演进与多版本适配路线（先从简，后扩展）

针对第三方 Agent 未来版本升级可能带来的配置字段变动（如键名重命名、结构嵌套层级变化），ACM 确立**“MVP 单一最新版，后期策略扩展”**的极简演进原则：

1. **MVP 阶段（先从简 · 拒绝过早优化）**：
   * 适配器仅面向本机**当前最新稳定版**进行单一路线实现（约 100–200 行 Python），不预写任何版本分支与探测逻辑；
   * 若用户环境存在未知/破坏性 Schema 变动，安全引擎以 `ERROR` 态安全阻断，绝不盲写破坏文件，提示用户升级 ACM 或上报 Issue。
2. **后期演进（后扩展 · 局限于模块内部）**：
   * 当未来某款 Agent 出现广泛的新老版本长期共存诉求时，**仅在该 Agent 的独立模块内部**引入基于 AST 结构特征的策略分发（Strategy Pattern），Adapter 对外 Protocol 契约与 Safety Engine 核心保持 100% 不变。
